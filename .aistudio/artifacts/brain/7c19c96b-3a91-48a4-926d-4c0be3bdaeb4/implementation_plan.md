# Dayseed — Phase 1 Implementation Plan (Revision 7: Owner decisions resolved)
## Domain Model, Data Integrity, Historical Records, SQLite v3, Repository & Undo

**Revision 7 — complete implementation specification (2026-11-02).**
This document replaces earlier plan revisions as the authoritative Phase 1 implementation specification. It incorporates all owner decisions (`U-1` through `U-13`), removes the rejected `habit_pauses` table design in favor of derived lifecycle pause ranges (`U-9`), and preserves the audited baseline at commit `097f314e068d4f30db78ba4728729e8e01f10737`.

## 1. Resolved Owner Decisions (`U-1` through `U-13`)
- **U-1 (Retroactive `REST_DAY`):** **Option A — Today only.** `REST_DAY` creation is accepted only for today's local date, only when eligible under its schedule (including any non-paused day in a `FLEXIBLE_WEEKLY_TARGET` week), and only when no same-date activity exists. Past/future `REST_DAY` requests are rejected. Backdated real activity remains allowed under `D-188` and may recalculate `MISSED` history, but cannot cross lifecycle closures (`PAUSED`, `ARCHIVED`, `COMPLETED`).
- **U-2 (Unscheduled bonus completion):** **Option A — Full completion can start/extend.** For `DAY`-period habits, a full qualifying completion on an unscheduled date may start or extend the streak and counts as one full completion (`completedStreakCount += 1`). Does not apply to `WEEK`-period target totals.
- **U-3 (Mid-week habit creation):** **Option A — Hold incomplete creation week.** A weekly habit created after the week begins is not penalized for pre-creation dates; its first partial week is held if below target and qualifies if it reaches the full target.
- **U-4 (Remaining weekly opportunities excepted):** **Option A — Hold the week.** If a weekly target remains unmet and every remaining eligible scheduled opportunity after the last real activity is covered by `REST_DAY` or `PAUSED` lifecycle dates, hold the week without lowering the target or awarding completion.
- **U-5 (Pause spanning partial weekly periods):** **Option A — Hold both partial weeks; close the run.** Pausing closes the active run immediately with terminal reason `PAUSED` (`broken_on_local_date = NULL`). Incomplete pre-pause and post-resume weekly portions are held if below target; a post-resume partial week may start a new run if it reaches the full target. The same run never bridges a pause.
- **U-6 (Lifetime goal meaning):** **Option A — Distinct active calendar dates.** `lifetime_goal_days` counts distinct local dates with real qualifying activity (positive numeric entry, valid completion outcome, or valid `EFFORT_AWARE` logged level including `TINY`). Excludes explicit zero alone, notes, `REST_DAY`, or pause dates without activity. Display as `X / N active days`.
- **U-7 (Unscheduled partial activity):** **Option A — Hold only an existing run.** Positive partial activity on an unscheduled `DAY`-period date may hold an already-open run and advance its continuity endpoint, but cannot start a run or increment `completedStreakCount`. Explicit zero is neutral.
- **U-8 (`EFFORT_AWARE` qualification):** **Option A — `USUAL`/`EXTRA` full, `TINY` partial.** `USUAL` and `EXTRA` qualify as full completion. `TINY` is partial progress (holds an existing run without incrementing `completedStreakCount` or starting a run, while counting as real activity for `lifetime_goal_days`).
- **U-9 (Pause source of truth):** **Option A — Existing lifecycle history only.** `habit_versions.lifecycle_state` is the single source of truth. Do NOT create a `habit_pauses` table or `PAUSED` rows in `habit_date_exceptions`. Derive pause ranges in memory (`derivePauseRanges(habitVersions)`) from contiguous effective-dated `PAUSED` slices.
- **U-10 (Historical week boundaries):** **Option A — Preserve history.** Create `week_start_history` in SQLite v3. A week-start preference change finishes the current 7-day period, schedules the new preference on the first date strictly after that period ends whose ISO weekday matches the new week-start day, and treats any intervening days as a neutral transition interval. Seed one legacy baseline row (`is_legacy_baseline = 1`) during v2→v3 migration.
- **U-11 (Schedule × target period):** **Option A — `target_period` controls cadence; `schedule_kind` controls eligibility.** Every `target_period = DAY` habit uses daily evaluation and `StreakUnit.DAYS`. Every `target_period = WEEK` habit uses weekly evaluation and `StreakUnit.WEEKS` (including v2-legal `DAILY`+`WEEK` and `SELECTED_WEEKDAYS`+`WEEK` rows).
- **U-12 (Mid-week target/unit change):** **Option B — Same-unit target saved tomorrow; evaluation frozen; unit change deferred.** A same-unit target change may be saved effective tomorrow, but the in-progress week retains the target/metric snapshot from its start; the new target governs the next week. A `unit_code` or `tracking_mode` change on a weekly habit is deferred to the next weekly boundary.
- **U-13 (Sub-seven-day run history):** **Option B — Preserve separately from Grove.** Keep a closed run that did not reach Grove qualification (`elapsedActiveCalendarDays < 7`) in `habit_streak_runs` with `tree_state = 'UNQUALIFIED_HISTORY'` and its `terminal_reason` (`MISSED`, `PAUSED`, `ARCHIVED`, `COMPLETED`). Qualified closed runs use `DORMANT_TREE`.

## 2. Implementation Sequence
1. **Step 1 — Domain Types and Pure Validation (`Models.kt`):**
   - `DayseedNumericRangeException`, `Cursor.getValidatedInt` / `getNullableValidatedInt`, `LocalDateValidator`, `TrackingMode.creatableModes`, 8-constant `ProgressBand` (`ZERO`, `TINY_STEP`, `GETTING_STARTED`, `HALFWAY`, `ALMOST_THERE`, `GOAL_MET`, `EXTRA`, `HUGE`) with paired `encouragementQuote` and `motivationQuote`, `BigInteger`-based `ProgressBandClassifier`, `CompactHistoryBucket`, `DayRecordState`, `DerivedPauseRange` & `derivePauseRanges`, `HabitDateException`, `HabitStreakRun`, `WeekStartPolicyEntry`, `HabitConfigEffectivePolicy`, `HabitConfigurationLockedTodayException`, `HabitSummary`, and `HabitDeletionPayload`.
2. **Step 2 — SQLite v3 Schema & FK-Cascade-Safe Migration (`DayseedDatabaseHelper.kt`):**
   - 15 v3 tables (12 existing + `habit_date_exceptions`, `habit_streak_runs`, `week_start_history`), 13 named explicit indexes, 4 cross-table triggers, `ALTER TABLE habits ADD COLUMN category / lifetime_goal_days` without dropping `habits`, strict `DAYSEED_META:` parser, and fail-closed v2→v3 migration.
3. **Step 3 — Streak & Grove Engine (`StreakAndGroveEngine.kt`):**
   - Pure evaluation and SQLite persistence engine implementing `U-1`..`U-13`, `D-188` backdated recalculation with deterministic run-identity preservation, 7-calendar-day Grove qualification, and normalized mixed-cadence longest streak ranking.
4. **Step 4 — Repository Integration, Undo & Backup (`DayseedRepository.kt`):**
   - Complete transactional `D-194`, `U-12` weekly configuration deferral/freeze, `setRestDayExceptionSync` (`U-1`) + automatic clearing on real activity (`D-218`), `setWeekStart` (`U-10`), `deleteHabitWithUndoSync` + `HABIT_DELETION` undo with collision guards, and v2/v3 portable backup export/import.
5. **Step 5 — UI & ViewModel Integration (`DayseedViewModel.kt`, `HabitCard.kt`, `AddEditHabitDialog.kt`, `TodayScreen.kt`):**
   - Expose `habitSummaries`, `BigInteger` progress totals/percentages and paired quotes, `creatableModes` in new-habit dialog, `REST_DAY` toggle on Today, `NO_RECORD` vs `EXPLICIT_ZERO`, streak/Grove indicators, and `lifetimeGoalDays`.
6. **Step 6 & 7 — Regression Test Suite (`T1-01`..`T1-36`) & Build Verification:**
   - Execute full unit/Robolectric suite and `assembleDebug` with inspected evidence.
