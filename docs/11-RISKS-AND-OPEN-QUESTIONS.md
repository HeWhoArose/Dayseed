## Data-model design status

**Exact v1 relational schema: proposed, partially reviewed, not approved for implementation.** A concrete candidate has been added to `03-TECHNICAL-ARCHITECTURE.md`. Partial owner decisions are approved: effective-dated habit configuration snapshots preserve historical meaning; numeric/duration entries are stored separately from single-per-day completion-only/effort-aware outcomes (D-189); and D-192 confirms both optional per-entry notes and one optional habit/date context note. The proposed domain rules must validate records against the effective tracking mode and reject contradictory combinations. Habit-note cardinality is resolved: the optional habit/date note is unique per habit/local date and is independent of any per-entry note or general journal entry. D-191 approves structured schedule columns and their semantics: `DAILY` means every local calendar day with a `DAY` target; `SELECTED_WEEKDAYS` requires a non-empty mask and a `DAY` target; `FLEXIBLE_WEEKLY_TARGET` uses a `WEEK` target and optional preferred weekdays only as guidance. D-195 approves a stable, locale-independent 7-bit weekday-mask encoding; its constraints and behavior still require technical validation. D-190 approves stable UUID identity plus nullable idempotency keys unique when non-null, with the same key reused only for retries of the same logical submission and a new key for each distinct intentional entry. Because numeric entries and non-numeric outcomes are separate tables, docs 03/30 now propose cross-table insert/update guards plus a domain-transaction check in addition to table-local partial unique indexes; this enforcement remains proposed and unverified until full schema review and later authorised tests. D-188 resolves the prior explicit-miss transition question: do not store a user-entered miss; derive missed status after a scheduled day passes without qualifying activity, allow genuine backdated activity to recalculate that date, and never let journal memos change habit status. Do not implement the candidate or migrate the existing version-1 database until owner approval and a separate technical-validation authorisation.

D-194 resolves repeated Apply-today edits: the first change creates today's version; a subsequent same-day change replaces it only when no qualifying habit activity has been recorded today; after activity exists, preserve today's configuration/history and offer Apply tomorrow; Cancel changes nothing; Apply tomorrow creates or updates tomorrow's not-yet-effective version. The previously open habit-linked notification cleanup question now has a delegated schema default documented in `03-TECHNICAL-ARCHITECTURE.md` and `30-SCHEMA-CLOSURE-AND-MIGRATION-PLAN.md`: queue only opaque notification IDs in an outbox, remove habit-owned DB rows transactionally, preserve journal entries/global reminders, cancel OS notifications after the commit, retry on startup, and suppress stale posting by checking that the habit is still active. This is not implemented or verified; the owner may override it before complete schema approval. D-195 resolves the weekday-mask encoding policy; technical validation remains pending. D-193 resolves the skipped-state policy: no explicit habit-day Skip action or persisted skipped outcome in v1. The schema remains proposed and awaits authorised technical validation.

## 2. Open product questions

1. **Schedule types — policy approved by D-191:** `DAILY` runs every local calendar day; `SELECTED_WEEKDAYS` runs only on its configured non-empty weekday mask; `FLEXIBLE_WEEKLY_TARGET` uses a weekly target and optional preferred weekdays only as guidance. D-195 approves a stable, locale-independent 7-bit weekday-mask encoding (Monday=1 through Sunday=64); technical verification remains pending and the approved schedule policy is not being reopened.
2. **Outcome semantics — policy resolved:** explicit zero differs from no record (D-023); rest/non-scheduled days and paused periods have distinct neutral/excluded meanings (D-027); missed status is derived after a scheduled day passes without qualifying activity (D-188); and D-193 confirms no explicit habit-day Skip action or persisted skipped outcome in v1. No user-entered “miss” outcome is allowed. Remaining work is to verify implementation and keep the proposed schema/test contracts aligned after the separate validation gate.
3. **Progress labels:** thresholds and labels are documented in D-040; user-customisable labels remain open and should not be assumed for v1.
4. **Multiple records — resolved:** legitimate multiple numeric entries/duration sessions can occur on one local date and are summed; retries of the same logical action must remain idempotent (D-023, D-031, D-032).
5. **Journal multiplicity — resolved in the planning baseline:** multiple journal entries per date are allowed; confirm create/edit/delete and draft behavior in the detailed data contract.
6. **Date/time policy — baseline approved (D-187):** local date keys are separate from event instants; preserve historical dates across timezone travel; handle clock uncertainty conservatively; allow explicit backdating; and use the saved week-start consistently. Remaining work is technical edge-case verification for clock/timezone changes, reminder/catch-up deduplication, and date boundaries—not another owner policy choice.
7. **Habit lifecycle — baseline approved (D-187):** archive by default to preserve accessible history; permanent deletion is a separate, clearly explained action. Remaining work is to finalise deletion confirmation/retention wording and verify export/backup and derived-summary behaviour; independent journal entries must remain intact.
8. **Backup/export — policy largely approved; mapping and technical verification remain:** readable journal export and complete versioned portable backup are required. Replace/Merge, safety backup, integrity/compatibility stop rules, password-protection direction, backup scheduling/retention, and the main conflict-preservation choices are recorded in D-091–D-145. D-186 separately resolves the Android platform-backup policy: exclude sensitive Dayseed data by default. Before the planning gate, review the proposed entity-category mapping in `30-SCHEMA-CLOSURE-AND-MIGRATION-PLAN.md`, finish its serialized field-level contract and version-compatibility boundary, and define safe handling for record-type conflicts where keeping both cannot coexist. After separate authorisation, verify actual export/restore, migration and Android backup/device-transfer behaviour.
9. **Encouragement — direction approved; routine cadence delegated:** outcome-aware and comeback behaviours have specific decisions. D-196 documents a default for optional-tip cadence, opt-out, and dismissal/suppression; remaining work is final non-shaming copy and cross-document consistency, not a separate owner choice.
10. **Reminders — core trigger/count rules approved; shared-delivery defaults documented:** onboarding opt-in, per-habit default time, weekly-goal trigger/catch-up rules and inactivity caps are recorded. The weekly reflection's clock time remains an owner choice and must not be inferred from the per-habit 9:00 a.m. default. D-196 defaults cover editable 21:00–08:00 quiet hours, a shared three/day cap, per-habit/day cap, collisions, deduplication, local-only timing learning and rollback. Android permission, timezone, delivery and reboot behaviour still require post-gate validation.
11. **Monetisation — resolved for initial v1:** D-200 defers ads until a pre-launch revisit. No SDK, placement, rewarded ads, purchases, subscriptions or Supporter Pack is approved for initial v1. Keep docs/33 as future review material. Any later monetisation requires a new explicit decision and current privacy, consent, accessibility, offline and Play-policy evidence.
12. **Visual direction (D-008):** confirm the broad visual identity or explicitly defer it; W1/N1/A2 and modified G2/G3 remain the selected planning directions. Do not reopen settled Growth Mark semantics without a material reason.
14. **Comeback trigger/episode policy resolved:** D-047–D-056 and D-146–D-160 approve the 14-day and 30-day triggers, 30-day precedence, and once-per-qualifying-episode suppression. Remaining question is presentation/copy and accessibility, not whether to show the approved experiences. See `29-UX-DESIGN-APPROVAL-PACK.md`.
14. **Typography/colour (D-019):** decide whether exact tokens are required before the planning gate or explicitly deferred; system typography and system light/dark appearance remain the accepted baseline.
15. **Minimum Android version and physical-device matrix:** technical validation item after separate authorisation; do not require premature device testing to complete planning.

### Retrospective journal prompt — delegated default

D-042 approves the optional direction. Under D-196, the default cadence in docs 09/24/26/28 is one non-blocking in-app prompt on the first eligible app opening for the most recent fully completed local date with no saved entry; at most once per date, no notification/backlog, reuse a same-date draft, and no stacking with comeback. It is not a separate Gate A blocker; the owner may override or defer it in the grouped review. The prompt is not implemented and its acceptance cases are planned, not executed.

## 3. Technical and operational questions

- **Stack direction resolved (D-009):** continue native Kotlin + Jetpack Compose. Build, test, APK-install, and device readiness remain unverified and must wait for explicit validation authorisation.
- What database and migration library are supported by the selected stack at implementation time?
- How will Android platform backup and device-to-device transfer interact with the privacy promise, separately from the user-controlled local backup file?
- Before any later premium online backup/cross-device sync release, what provider, consent UX, security/threat model, data-flow, deletion/retention, conflict-resolution, recovery, and monetisation design is approved? This is explicitly outside initial v1.
- Is database encryption needed for the threat model, and what are the usability/recovery costs?
- How will exports be versioned and validated?
- What happens when storage is nearly full or writes fail?
- Current working environment is AI Studio and GitHub `main` is canonical. Revisit only if access or workflow changes; always reconcile the latest remote state before continuing.
- What exact evidence constitutes a verified native Android milestone?

## 4. Decision rules

Resolve questions that affect data integrity, privacy, daily record semantics, or app architecture before implementation. Lower-risk visual details can be explored with prototypes, but should not be silently finalised by an implementation agent. If a question is deferred, record the chosen safe default and the reason in the decision log. Planning completion does not itself authorise implementation; owner approval must be explicit.
