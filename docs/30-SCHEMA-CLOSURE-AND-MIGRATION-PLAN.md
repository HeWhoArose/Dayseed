# Proposed Schema Closure, Transaction, and Migration Plan

**Review date:** 2026-10-27  
**Status:** Proposed planning addendum; **not approved for implementation**. No database schema, migration, application code, or tests were changed or executed by this document.

**Authority:** The approved owner choices remain in the [Decision Log](09-DECISION-LOG.md). The current table proposal remains in [Technical Architecture](03-TECHNICAL-ARCHITECTURE.md). This document identifies refinements and acceptance requirements needed to make that proposal coherent. Any disagreement must be reconciled in both documents before the owner approves the complete schema.

## 1. What is already settled

The schema must preserve the following owner-approved rules:

- D-187: local calendar date keys are separate from instants; saved date keys stay stable through timezone travel; historical settings remain effective-dated; archive preserves history; permanent deletion is separate; backdating is explicit.
- D-188/D-193: missed is derived after a scheduled day passes without qualifying activity; no stored user-entered miss and no explicit habit-day Skip action/outcome in v1.
- D-189: numeric/duration activity entries are separate from non-numeric day outcomes; multiple numeric entries per habit/date are valid; completion-only/effort-aware outcomes have at most one current outcome per habit/date.
- D-190: stable UUID identity; same logical retry reuses its idempotency key/identity; distinct intentional activity gets a new key.
- D-191/D-195: DAILY, SELECTED_WEEKDAYS, FLEXIBLE_WEEKLY_TARGET; target period DAY or WEEK as specified; fixed Monday-first weekday mask and invalid mask/schedule combinations rejected.
- D-192: optional per-entry notes and one optional habit/date note can coexist.
- D-194: same-day Apply-today replacement is allowed only before qualifying activity exists today; after qualifying activity, preserve today and offer Apply tomorrow.
- D-186: the Android platform-backup exclusion policy is approved; actual manifest/data-extraction behaviour must be validated separately after authorisation.
- D-091–D-145: portable backup and restore policy is defined at the product level, including full approved coverage, integrity/compatibility checks, Replace/Merge, safety backup, conflict preservation, password-protection direction, and Auto Backup controls.

These approvals do **not** approve the complete schema or prove they are implemented correctly.

## 2. Recommended model refinements to reconcile into the architecture proposal

These are schema recommendations based on approved behaviour, not new owner-approved decisions.

### 2.1 Habit lifecycle and effective-dated configuration

- Treat each configuration version as the source of truth for the state applicable to a local date. Use an explicit lifecycle enum capable of representing ACTIVE, PAUSED, COMPLETED, and ARCHIVED so the approved no-active-habit comeback timer can be calculated from the real effective state.
- **V1 schema default: omit `archived_at_utc_ms` from `habits`.** The current lifecycle state is derived from the latest effective `habit_versions.lifecycle_state`; no second archive projection is stored. This avoids duplicated state and matches the canonical architecture proposal.
- Each habit must have one unambiguous effective configuration for each date. Enforce uniqueness of the pair (habit_id, effective_from_local_date). Resolve historical configuration by selecting the latest version whose effective date is not after the selected record date.
- Preserve historical configuration: do not overwrite a version whose effective date is in the past or whose current-date configuration has already been used by qualifying activity. Under D-194, the current local date's version may be replaced by a repeated Apply-today edit only while no qualifying habit activity has been recorded on that date. Once activity exists, preserve the current-date version and offer Apply tomorrow; a future version may be revised while it is still not yet effective. The unique `(habit_id, effective_from_local_date)` constraint ensures only one version per effective date.
- The three D-191 schedule kinds are the approved v1 set. Every-N-days and optional-start-date schedule patterns mentioned in the 2026-10-18 implementation audit are historical proposals and must not be added unless the owner revises the decision log.

### 2.2 Numeric and non-numeric habit records

- Numeric/duration entries use stable UUIDs, a habit ID, ISO local-date key, non-negative whole-number value, optional entry note, creation/update instants, and nullable idempotency key.
- A partial unique index should enforce uniqueness of each non-null idempotency key within numeric entries. Never deduplicate solely because two values or timestamps look similar.
- Non-numeric day outcomes use stable UUIDs, a habit ID, local-date key, explicit outcome kind, optional effort level, creation/update instants, and retry identity/idempotency metadata consistent with D-190. Enforce at most one current outcome per habit/date.
- Completion-only outcomes must not invent an amount or effort score. Effort-aware outcomes must use a valid approved effort value. Quantity/duration records must not satisfy a non-numeric mode, and non-numeric outcomes must not satisfy a quantity/duration mode.
- A table-level unique constraint cannot by itself prevent a cross-table conflict between a numeric entry and a non-numeric outcome for the same habit/date. The write transaction must validate the effective tracking mode and reject contradictory records without altering the prior saved state.
- Numeric daily totals and weekly summaries remain derived from source entries and effective configuration. Do not store a second authoritative total that can drift from those entries.

### 2.3 Journal records and optional habit link

- Saved journal entries use a stable ID, explicit local date, non-whitespace body, optional title, optional primary/secondary mood codes, optional prompt identifier, and creation/update instants. Multiple entries on one date are allowed.
- A saved journal entry's optional habit link must not make the entry dependent on the habit's continued existence. Proposed refinement: a nullable linked_habit_id foreign key with ON DELETE SET NULL, so permanent habit deletion removes the relationship but preserves the journal entry, text, date, title, and mood tags. No journal entry or draft is deleted merely because a habit is archived or deleted.
- A journal edit preserves ID and original creation instant. A deliberate journal date change affects only the journal entry; it never moves habit records.
- A comeback draft is not a saved journal entry. Add optional `intended_journal_entry_id` (stable UUID) to `journal_drafts`; assign and persist it when a save is first prepared, then reuse it on retry. Add a partial UNIQUE index for non-null intended IDs so two drafts cannot claim the same future journal-entry identity. Saving the journal entry and removing/resolving the source draft must be one transaction. If saving fails before commit, leave the draft and its intended ID intact; after commit, the saved entry is visible in Journal and the draft is resolved. An uncertain caller must inspect persisted state and must not generate a new ID.
- Journal body validation must reject whitespace-only text at the domain boundary; a database check should reject ordinary empty/space-only values as defence in depth.

### 2.4 Backup-conflict records and notification cancellation

- Replace/Merge decisions require unresolved conflicts to survive later app restarts. The existing table list does not yet model this explicitly. Proposed addition: a durable restore-session record and a restore-conflict table that preserve the conflicting record type/key and both validated versions. A conflict row exists only while a user decision remains unresolved; do not store a separate conflict-status column. On successful resolution, apply the selected result and delete the conflict row atomically. Store any journal text only in local protected app data, never logs or notification text.
- A conflict record should remain discoverable in Settings → Backup & Restore. Keeping both journal versions creates separate entry IDs. Tracking conflicts must never be auto-added together. A record type that cannot safely keep both remains unresolved or stops safely; it must not silently select a winner.
- Database transactions cannot make Android's external notification manager part of the SQLite commit. Proposed deletion refinement: within a database transaction, gather opaque IDs/tags for a habit's pending/posted notifications into a small cancellation outbox and remove the habit-owned records/ledger plus habit identity; preserve independent journal entries and global reminders. After commit, cancel the OS notifications and remove outbox rows only after successful cancellation. If cancellation fails or the app stops, retry from the outbox on the next app start; any delivery worker must check that the habit still exists and is active immediately before posting. The outbox should retain only opaque cancellation identifiers, no habit name or journal text.
- Do not transfer OS-specific scheduled-notification IDs as portable data. Preserve logical reminder-delivery keys/status where needed for deduplication, then rebuild eligible future scheduling on restore from current settings and source records.
- The outbox is technical cleanup state, not a user record. Its retention must be limited to the minimum needed for reliable cancellation.

#### Proposed record-type conflict mapping — owner review required

The following mapping applies D-094–D-102 to the proposed schema. It is a conservative reconciliation proposal, not a new owner-approved conflict policy.

| Record type | Proposed restore/merge treatment | Safety boundary |
|---|---|---|
| Same stable ID and same validated contents | Deduplicate as one logical record. | Do not use similar text/value/timestamp as a substitute for stable identity or an approved logical key. |
| Same stable ID but different validated contents | Preserve both payloads in `restore_conflicts`; do not auto-select or overwrite. | This is one record-identity conflict keyed by the stable ID. If the two payloads also carry the same idempotency key, resolve that key constraint within this same conflict; do not create a second duplicate conflict row for the same two candidate versions. Revalidate all uniqueness constraints before committing a choice. The conflict stays reviewable across restart until an explicit choice commits. |
| Same non-null idempotency key attached to different stable IDs or materially different payloads, including a collision between `habit_entries` and `habit_day_outcomes` | Preserve the colliding submissions as one canonical `ACTIVITY_IDEMPOTENCY_KEY` conflict using the collided key as `record_key`; do not count them as two activities or silently discard one. | Because the idempotency key is globally unique across logical activity submissions, the collision must be resolved before either conflicting candidate is applied to the live tables; a retry may not be reclassified as a distinct intentional action without explicit evidence. Do not create separate conflict rows keyed by different source-table names for the same collided key. If the same stable-ID pair is already represented by one record-identity conflict, consolidate the overlap there rather than storing duplicate conflicts for the same candidates. |
| Journal entries | Offer current, backup, or both as separate journal entries with distinct stable IDs, as approved by D-097. | “Both” means two independent entries; never merge their text into one entry. |
| Habit/date context notes | Preserve both snapshots in the unresolved-conflict record when the same note ID has different content or two IDs collide on the unique (habit_id, local_date) key. Offer current or backup as the live note choice; do not offer “both” while the one-note-per-habit/date constraint applies. | Neither candidate changes activity totals or outcome state. Do not discard the unchosen text until the selected resolution commits; failure leaves the conflict reviewable. |
| Habit definitions and effective-dated configuration | Compare conflicting definitions/versions side by side and let the user choose; separate habits may be preserved where appropriate, as approved by D-099. | A same-ID configuration conflict must not create two effective versions for the same habit/date or reinterpret historical records. If a safe separate-habit remap cannot be established, keep the conflict unresolved until a supported choice is made. |
| Preferences/settings | Show current and backup values and require explicit selection, as approved by D-100. If settings retain an Auto Backup opt-in/frequency but the restored destination or permission is unavailable, leave scheduled writes paused until the user explicitly reselects/re-authorises a destination. | Do not duplicate a setting key, silently prefer one source, write to a fallback destination, or treat the presence of stored preferences as proof the destination is authorised. |
| Unfinished comeback drafts | Preserve both conflicting versions for later review, as approved by D-101. | Keep drafts separate from saved journal entries and do not auto-promote either version into Journal. |
| Corrupt, incomplete, or unsupported backup/schema version | Stop before live mutation, as approved by D-102. | Do not treat an unsafe file as an ordinary merge conflict or leave partial restored data. |

For all conflict types, clear the conflict payload only in the same successful transaction that commits the selected resolution. A failure leaves the conflict available for review. The specific options presented must be generated from the record type's safe capabilities, not show a generic “Keep both” choice when the schema cannot safely support it.



## 3. Candidate relational invariants

The following SQL/domain invariants should appear in the final architecture model and acceptance plan.

### 3.1 Effective-dated habit versions

- Primary key: stable version UUID.
- Foreign key: habit ID references the parent habit; a permanent parent deletion removes its owned versions.
- Unique: (habit_id, effective_from_local_date).
- Required: valid local date, non-empty name, valid tracking mode, valid target period, positive integer target value, and valid lifecycle/reminder enum values.
- Quantity/duration modes require a valid unit code. Completion-only/effort-aware modes do not use a fabricated numeric unit.
- Schedule-kind/target-period/mask combinations:
  - DAILY: target period DAY; scheduled mask NULL; preferred mask NULL.
  - SELECTED_WEEKDAYS: target period DAY; scheduled mask in 1–127; preferred mask NULL.
  - FLEXIBLE_WEEKLY_TARGET: target period WEEK; scheduled mask NULL; preferred mask NULL or in 1–127.
- Every present mask must contain only the seven approved bits. Because the mask is one integer, reject unknown higher bits and invalid combinations rather than silently trimming them.
- For flexible weekly completion-only/effort-aware goals, target value represents a count of qualifying completed dates, not a numeric amount of work. The UI/domain validation must keep the meaning of target value mode-specific.

### 3.2 Entries and outcomes

- Numeric entry value must be an integer greater than or equal to zero; negative values are rejected without changing saved data.
- D-190's approved rule is that a non-null idempotency key identifies one logical activity submission across the separated activity tables, not merely within one table. Use a partial UNIQUE index for non-null keys within each of `habit_entries` and `habit_day_outcomes`, plus cross-table INSERT/UPDATE guards (or an equivalently verified database-level mechanism) that reject a key already present in the other table; perform the same check in the domain transaction. This closes the gap that table-local indexes alone cannot enforce global uniqueness. A retry reuses the same key/ID; a distinct intentional record gets a new key/ID. Backup restore must treat cross-table key collisions as explicit conflicts and not import either duplicate as live activity until resolved.
- Completion-only day outcomes permit only the completion outcome and no effort value. Effort-aware outcomes require an allowed effort value. A unique constraint on (habit_id, local_date) prevents two current day outcomes for one habit/date.
- Do not permit contradictory numeric-entry/day-outcome combinations for the effective tracking mode. Validate inside the write transaction and roll back if any row fails.
- A note table has at most one habit/date note per (habit_id, local_date); entry notes remain on their specific numeric/duration entry and never become habit outcomes.
- Local date strings must be canonical ISO YYYY-MM-DD and validated as real dates by the domain layer. Creation/update instants are UTC epoch milliseconds; never use a converted UTC date as the stored local-date key.

### 3.3 Journal, settings, reminders and restore state

- Saved journal entry body is non-blank after validation; IDs remain stable across edits; multiple entries per local date are valid.
- Nullable linked_habit_id uses ON DELETE SET NULL; the entry has no cascade dependency on its habit.
- Settings use stable keys and validated value types. Do not put journal text inside generic settings values.
- Reminder delivery keys are unique per logical occurrence; delivery rows contain no personal message copies. Habit-linked delivery rows are deleted with that habit.
- Restore conflicts must preserve both validated versions until explicit resolution, and remain restorable/reviewable after process death. A failed restore must not leave live data partially changed. `restore_conflicts.restore_session_id` is a required foreign key to durable local restore-session context; the parent must not be deleted while unresolved child conflicts remain. Proposed session states are `IN_PROGRESS`, `RECOVERY_REQUIRED`, `COMPLETED`, `COMPLETED_WITH_CONFLICTS`, and `FAILED_SAFE`. After input validation and a verified safety backup, create and commit an `IN_PROGRESS` session row in a short standalone transaction before the live-data transaction. The single live Replace/Merge transaction must contain all live data changes, unresolved conflict rows, and the final `COMPLETED` or `COMPLETED_WITH_CONFLICTS` session state atomically. On an observed transaction failure, roll back all live data/conflict changes before marking the session `FAILED_SAFE` in a separate transaction. If the process stops before that status update, startup must verify the live transaction did not commit, then reconcile the still-`IN_PROGRESS` session to `RECOVERY_REQUIRED` and offer a safe review/retry path; never infer success or auto-run a second restore. After the last conflict is successfully resolved, change its parent from `COMPLETED_WITH_CONFLICTS` to `COMPLETED` in the same transaction. Portable backup exports only minimal context for a completed session that still has conflicts; on import, create a new local session ID and remap each conflict's parent reference. Never export active/incomplete transaction state or a device-local safety-backup reference.
- The notification-cancellation outbox uses a local stable `cancel_id`, non-null opaque platform tag and notification-ID pair, creation/last-attempt instants, attempt count, status and minimal error category. Enforce UNIQUE on the non-null tag/ID pair so duplicate queue attempts are harmless; retry outstanding cancellation idempotently and remove a row only after confirmed cancellation. Never include habit names, journal text or stable habit IDs in the outbox.
- All foreign keys must be enabled on each SQLite connection. Minimum indexes/constraints include: UNIQUE effective versions by habit/date; entries by habit/date/time; partial UNIQUE non-null idempotency keys in each activity table plus a cross-table key-collision guard; UNIQUE day outcomes by habit/date; UNIQUE habit/date notes; journal entries by date/time; drafts by updated time; pending reminder deliveries; restore conflicts by parent session and creation instant plus UNIQUE (restore_session_id, record_type, record_key); restore sessions by state/update instant; and cancellation outbox pending rows with a UNIQUE opaque platform tag/notification-ID pair.

## 4. Transaction boundary map

| Operation | Required atomic database work | Failure rule |
|---|---|---|
| Create habit | Insert stable habit identity and its initial effective configuration version together | No partially created habit; retry uses the same stable identity |
| Save numeric entry | Validate current effective configuration and unit; insert one entry; update only rebuildable caches if any | No success before commit; retry of the same logical submit counts once |
| Save/edit day outcome | Validate mode and existing numeric rows; insert/update the single current outcome | Reject contradictory/out-of-mode writes and roll back |
| Edit/delete one record | Update or delete only the selected stable ID; invalidate/recompute dependent summaries | Unrelated records remain untouched |
| Change schedule/target | Apply D-194 effective-date rule and write/revise the applicable version | No past record/config reinterpretation; Cancel means no change |
| Save journal entry/draft | Save entry and resolve/remove the source draft in one transaction; preserve stable intended ID | Failure before commit leaves the draft unchanged; retries cannot duplicate |
| Archive/pause/complete/reactivate | Change effective lifecycle state and its effective timestamp/date in one transaction | History stays accessible; active/no-active timer recalculates from effective state |
| Permanently delete habit | Transactionally queue opaque notification-cancel IDs, delete habit-owned tracking/configuration/delivery records, null optional journal links, and delete the habit | Independent journal entries/global reminders survive; cancellation outbox retries separately |
| Create backup | Produce a consistent snapshot of the approved backup data set, write, close, and read/verify output before reporting success | Never present a partial/unverified file as valid; source database unchanged |
| Restore Replace/Merge | Fully validate the file and require a verified safety backup; then persist an `IN_PROGRESS` session in a short separate transaction. Apply all restored records, fresh local conflict-bearing session context, unresolved conflicts and the final `COMPLETED`/`COMPLETED_WITH_CONFLICTS` session status in one atomic live-data transaction; remap imported conflict parent references to the new local session ID | Invalid file or failed safety backup changes no live data and creates no runnable restore. A live-data transaction error rolls back the whole operation; then mark `FAILED_SAFE`. If the process stops before that status update, startup verifies rollback and marks the durable session `RECOVERY_REQUIRED`. Never leave partial live data or a misleading completed session |
| Resolve one conflict | Validate and write the chosen result(s), delete only that unresolved conflict row, and set the parent session to `COMPLETED` only if no unresolved child rows remain—all in one transaction | Keep both source versions and the parent review context until the selected resolution commits; on failure, preserve the conflict row, payload snapshots, and parent state |

The delegated recovery default under D-196 is: after a successful single-record tracking mutation (create/log/complete/edit of one numeric entry, day outcome or habit/date note), show one 8-second snackbar Undo. The token references the exact stable entity and mutation; a new mutation replaces the previous pending token. Undo runs in a guarded transaction: creation removes only the record created by that action; edit restores captured prior fields only if the entity still has the expected post-edit version. If another change makes the inverse unsafe, do not overwrite newer data; direct the user to normal History correction instead. Undo is in-session only; after timeout or process death, committed state remains and the Undo affordance disappears. For deletion of one selected numeric/duration entry, a clear contextual Delete action plus immediate Undo is sufficient; do not add a second confirmation dialog. Confirmed journal-entry deletion, permanent habit deletion, delete-all and Replace/Merge restore remain explicitly confirmed/non-undoable. These defaults are reversible and may be overridden by the owner before Gate A. Never show Undo until the original mutation commits; a failed/uncertain save preserves the prior data and offers recovery rather than false success.

## 5. Portable backup mapping

Readable journal export is not the same artifact as the full Dayseed portable backup.

**Readable journal export (v1):** saved journal entries only, including local dates, optional title, text and recorded mood tags. Do not silently include unsaved comeback drafts or reminder metadata. It does not delete or alter source records.

**Portable Dayseed backup (v1):** map every included entity/relationship explicitly using stable IDs and a dedicated versioned format. The following is the proposed field-level contract; it supplements, and does not override, the approved category/safety rules in D-091–D-145.

| Entity/category | Portable fields and relationship rules | Restore validation / transformation |
|---|---|---|
| Backup envelope | Dedicated Dayseed extension; distinct `format_version` and `schema_version`; creation instant; integrity metadata; category/count summary. Count live entities separately from unresolved conflict records/snapshots and conflict-bearing restore-session context; conflict payload versions must not inflate live habit, tracking or journal-entry totals. If manually password-protected, include the format's encryption envelope metadata, never the password or key. | Verify integrity, decrypt before parsing when applicable, validate supported versions and required fields, then check category counts against the validated payload. A damaged, unreadable or unsupported file stops before live mutation. |
| Habit identity and configuration versions | Stable habit IDs and every effective configuration version with its version ID, parent habit ID, effective local date, name/description, tracking mode, unit, target period/value, schedule kind, scheduled/preferred weekday masks, lifecycle state, reminder mode/time, and creation instant. V1 omits a separate `archived_at_utc_ms`; lifecycle is derived from effective versions. | Validate IDs and all D-191/D-195 mode/target/mask combinations. Preserve ISO local-date keys verbatim. Resolve conflicting same-ID versions without creating two versions for the same habit/effective date. If an explicitly supported keep-both choice creates a separate habit, create a new habit ID and remap all dependent habit-owned records consistently; otherwise keep the conflict unresolved. |
| Quantity/duration entries | Entry ID, habit ID, local-date key, whole-number value including explicit zero, optional entry note, creation/update instants, and nullable idempotency key. | Validate parent/reference, effective tracking mode, unit compatibility and key uniqueness. Preserve separate entries with distinct IDs/keys. A conflicting payload with the same entry ID or idempotency key is not added into the total; preserve it for explicit conflict resolution. |
| Completion-only/effort-aware day outcomes | Outcome ID, habit ID, local date, outcome kind, optional effort level where valid, idempotency key, and creation/update instants. | Validate mode-specific outcome fields and at most one live outcome per habit/local date. Never import a second competing outcome or fabricate numeric activity to resolve a conflict. |
| Habit/date notes | Note ID, habit ID, local date, text body, and creation/update instants. | Keep one note per habit/local date. Resolve same-ID or uniqueness collisions explicitly; do not let note text alter tracking totals/status. |
| Saved journal entries | Journal entry ID, local date, body, optional title, mood codes, prompt ID, optional linked habit ID, and creation/update instants. | Preserve local date, text, mood and stable identity. Keep current/backup/both options for genuine journal conflicts; “both” produces two distinct entry IDs and never concatenates text. If an optional linked habit is absent or cannot be mapped safely, set only that relationship to NULL; preserve the journal entry and text. |
| Unfinished journal/comeback drafts | Draft ID, optional local date, body, title/mood/prompt fields, optional stable `intended_journal_entry_id`, creation/update instants, and supported source context. Non-null intended IDs are unique across drafts. Keep drafts typed as drafts. | Preserve conflicting draft versions for review. Preserve the intended ID so retrying a prepared save cannot create a duplicate. Do not promote a draft to a saved journal entry or silently overwrite another draft. A draft stays local app data until explicit Save. |
| App preferences | Stable setting key and validated typed value for portable preferences approved by D-091–D-145, such as week-start, theme, reminder opt-in/quiet-hours preferences, and eligible backup preferences. | On key/value conflict, show current versus backup and require selection; never duplicate a key. Exclude credentials, secrets, premium purchase verification, provider access tokens and file-picker grants. If a destination/permission is unavailable on the receiving installation, ask the user to select/re-authorise it; keep scheduled writes paused until that succeeds and do not silently redirect. |
| Logical reminder-delivery ledger | Only the logical delivery key, type, optional related habit ID, intended local date/week key, and the minimum final/terminal status needed to deduplicate an already handled occurrence. | Validate keys and references. Do not restore active OS scheduling, platform tags/IDs, or unfinished daily reminders as runnable work. Re-evaluate current opt-in, current habit/goal state, local date/week, quiet hours and approved limits; rebuild only eligible future work. Keep enough history to avoid replaying a delivery already recorded as handled. |
| Unresolved restore conflicts | Conflict ID, required local `restore_session_id`, canonical record type/key, both complete validated payload snapshots, and creation instant. The row's existence means it is unresolved; do not store a separate status field. | Preserve both snapshots exactly as conflict evidence; do not use them as live activity rows until a supported resolution commits. On import, create a fresh local conflict-bearing restore-session record and remap each imported conflict's parent reference to it. Keep original payload IDs inside the snapshots; do not trust foreign keys inside an unresolved snapshot until resolution validates/remaps them. Delete the row only in the transaction that commits its supported resolution. |
| Restore-session context | Include only minimal context for a completed session that still owns unresolved conflicts: source session/bundle identifier, originating operation/format version, relevant created instant and validated category/count summary. Do not export an active/incomplete transaction's operational state or a local safety-backup reference. | Create a new local session ID for the imported conflict bundle; restore it as `COMPLETED_WITH_CONFLICTS` and preserve it while any imported conflicts remain unresolved. Do not present an interrupted in-progress restore as a portable successful snapshot. After the last child conflict resolves, set the session to `COMPLETED`; delete/archive its context only after the approved retention rules permit it. |
| Excluded technical/transient data | No active OS notification IDs/tags as portable scheduled work; no `notification_cancel_outbox`; no raw provider grants; no transient UI state; no cache-only totals; no secrets, passwords or purchase verification. Do not treat unresolved conflicts' local session pointer as a portable foreign key. | Rebuild derived totals/status from source records after restore. Keep the cancellation outbox on its source installation until cancellation succeeds; it is device-specific cleanup state and is never copied to the receiving installation. |

The file should carry a distinct `format_version` (container/serialization contract) and `schema_version` (entity/data contract), creation instant, an integrity value and a category/count summary. The proposed compatibility rule is: accept the current format/schema and any older version for which an explicit, loss-aware converter is documented; reject unknown or unsupported versions (including an unknown newer schema) before touching live data. If a required field cannot be mapped without loss, stop restore before live mutation. Do not silently drop or coerce records. A quarantine mechanism may be introduced only through a separately documented and reviewed design; it is not assumed to exist in the proposed v1 schema. If compatibility cannot be established or integrity fails, stop before live mutation. Manual password-protected backup needs a dedicated encryption envelope; the exact cryptographic parameters remain subject to a security review before release.


## 6. Proposed migration plan from the observed version-1 database

The read-only source audit dated 2026-10-18 reported SQLiteOpenHelper database version 1, a placeholder upgrade handler, and a daily_records table with a unique habit/date pair. Do not assume the observed schema has changed since that audit; inspect the actual checkout only after separate technical-validation authorisation.

1. **Design the versioned migration before code:** record the exact old schema and all current columns/indexes after the technical gate opens. Preserve v1 as the rollback source until the migration is fully verified.
2. **Create a deterministic mapping:** each existing daily_records row may become one numeric/duration entry or one appropriate non-numeric day outcome based on its actual saved tracking mode and value. A legacy daily aggregate cannot be reconstructed as multiple historical sessions; never invent sessions.
3. **Convert schedule representation explicitly:** translate the legacy selected-day representation to the approved Monday-first mask by mapping the actual stored weekday identities, not by assuming current locale or week-start.
4. **Fail closed on unmappable records (delegated planning default D-197):** missing habit parents, invalid dates, unsupported values, incompatible modes, and any other record that cannot be mapped losslessly must cause the whole migration transaction to roll back. Never drop, coerce, or invent activity history. Do not add a quarantine table by assumption; if inspection later shows rollback alone is insufficient, pause and present a separately reviewed recovery design before implementing migration.
5. **Migrate inside a controlled transaction:** create the new tables/indexes, migrate every source row, validate row counts and invariants, check foreign keys and recomputed totals, then advance the SQLite user version only after all checks pass.
6. **Prove rollback first:** use synthetic v1 fixtures with duplicate/zero/negative/corrupt values, each tracking mode, old weekday representations, orphan rows, and injected failure at every migration stage. Verify rollback preserves the v1 database and no partially upgraded version is presented as complete.
7. **Keep device/OS backup separate:** D-186 says sensitive Dayseed data should not be included in Android platform backup by default. Portable backup/restore coverage and actual platform exclusion must be tested separately, after authorisation.

No migration should be implemented from this document alone. The actual schema, wrapper/toolchain, and data quality must be inspected under the separate technical-validation gate before the migration is finalised.
