# Technical Architecture

**Status:** Repository now contains a native Android Kotlin/Jetpack Compose implementation. Architecture documentation is being reconciled against the actual code; design and data-contract gaps remain.

## Architecture goals
- Native-feeling Android-first experience.
- Local-first data access with reliable persistence.
- Core features available without network.
- Clear separation between UI, domain rules, and storage.
- Schema migrations and testable date logic.
- Minimal collection of personal data.
- A realistic path to iOS later without compromising Android v1.

## Approved stack direction
**Owner decision D-009:** Continue the existing native Android project using Kotlin + Jetpack Compose. The observed baseline includes Android `SQLiteOpenHelper`, a repository, ViewModel/StateFlow, and Compose screens. This is approval of the stack direction, not a claim that the project builds, passes tests, or is ready for feature work. The current database schema is version 1 and its upgrade handler is a placeholder; migration safety remains a planning/verification requirement.

No implementation should start based solely on this proposal.

## Layering
- **Presentation:** screens, accessible components, navigation, UI state.
- **Application/use cases:** create habit, record outcome, save reflection, edit history, calculate summaries, generate comeback message.
- **Domain:** habit schedules, daily outcome semantics, effort levels, date rules, summary calculations.
- **Persistence:** SQLite repositories, migrations, transaction boundaries, export and deletion.
- **Platform adapters:** notifications, app lifecycle, share/export, platform facilities if needed.

Domain logic should be testable without rendering UI or requiring network access.

## Local data model proposal
**Habit:** identifier, name, optional description, tracking mode, schedule, optional reminder configuration, created/updated timestamps, archived timestamp, and version metadata as appropriate.

**HabitRecord / tracking entry:** stable identifier, habit identifier, local date key, mode-specific value/outcome, optional effort level, optional entry-specific note, created/updated timestamps, and retry/idempotency metadata where needed. A habit may have multiple legitimate numeric/duration entries on one local date; sum distinct valid entries into the daily total while retaining each entry for correction. Do not impose a blanket unique constraint on habit + date. Protect against duplicate submission of the same logical entry with stable identity/idempotency rules. Explicit zero, completion-only state, effort-aware state, and no qualifying record must remain distinguishable. A missed scheduled day is derived from the applicable schedule and absence of qualifying activity after the day has passed; it is not a user-entered outcome.

**JournalEntry:** stable identifier, local date key, body, optional title, primary mood and optional secondary mood where present, optional prompt identifier, created/updated timestamps. Multiple entries per date are approved (D-170); editing preserves entry identity, and changing a journal date does not modify habit records. Unfinished drafts remain distinct from saved entries.

**Daily habit state / schedule interpretation:** derive scheduled-day status from the effective schedule/configuration and qualifying activity records. Rest/non-scheduled days are neutral; paused periods are excluded; before a scheduled day has passed, no record is merely unrecorded; after it passes with no qualifying record, derive missed status. Never offer a manual mark-as-missed action. Zero, partial, goal-met, above-target, completion-only, effort-aware, and unrecorded states remain distinct. Do not use a single uniqueness constraint to erase multiple entries or treat missing data as zero.

**Preferences:** explicit user settings such as theme, onboarding completion, and reminder preferences. Avoid storing derived metrics as source of truth if they can safely be recalculated.

The complete schema, exact constraints/indexes, transaction and deletion/cascade details, and migration strategy still require review. D-190 approves the stable-UUID and nullable idempotency-key policy, but its implementation is not verified. The current SQLiteOpenHelper schema is version 1 with a placeholder upgrade handler; no migration is verified.

Schema closure supplement: [Proposed Schema Closure, Transaction, and Migration Plan](30-SCHEMA-CLOSURE-AND-MIGRATION-PLAN.md) records proposed constraints, transaction boundaries, a field-level portable-backup mapping (including unresolved-conflict/session remapping and device-only exclusions), and migration acceptance requirements. Reconcile it with this table proposal before the owner approves the complete schema; it is not implementation approval.

## Proposed v1 relational schema — owner review required

**Status: Proposed, not owner-approved and not implementation-ready.** This design turns the approved product invariants into a concrete SQLite model while preserving the existing Kotlin + `SQLiteOpenHelper` stack. It must not be treated as permission to change code. Owner approval is needed for the key structure below; actual schema v1, migrations, and current source behaviour remain unverified.

### Tables and responsibilities

1. **`habits`** — stable identity: `habit_id` (UUID text primary key), `created_at_utc_ms`, `updated_at_utc_ms`, and optional `archived_at_utc_ms` only as a rebuildable current-state projection. The effective-dated `habit_versions.lifecycle_state` is the historical source of truth for `ACTIVE`, `PAUSED`, `COMPLETED`, and `ARCHIVED`. If retained, update the projection transactionally and never use it to reinterpret past dates. Permanent deletion is a separate explicit operation that removes the selected habit and its owned tracking/configuration data transactionally; it never deletes independent journal entries. Do not retain a tombstone after a confirmed permanent deletion unless a later privacy decision requires one.
2. **`habit_versions`** — effective-dated snapshots of the habit's user-facing configuration (immutable once effective): `version_id` (UUID primary key), `habit_id` (foreign key), `effective_from_local_date` (ISO YYYY-MM-DD), `name`, nullable `description`, `tracking_mode` (quantity, duration, completion-only, effort-aware), nullable `unit_code`, `target_period` (`DAY` or `WEEK`), positive integer `target_value` (targets must be greater than zero; activity values may be zero), `schedule_kind` (`DAILY`, `SELECTED_WEEKDAYS`, or `FLEXIBLE_WEEKLY_TARGET`), nullable `scheduled_weekdays_mask` (used only by `SELECTED_WEEKDAYS`), nullable `preferred_weekdays_mask` (optional guidance for `FLEXIBLE_WEEKLY_TARGET`, never a restriction), `lifecycle_state` (`ACTIVE`, `PAUSED`, `COMPLETED`, or `ARCHIVED`), reminder mode/time, and `created_at_utc_ms`. Unique constraint: (`habit_id`, `effective_from_local_date`); an edit effective on an existing version date replaces that not-yet-effective version inside a transaction, rather than creating ambiguous versions. Past versions remain unchanged. Store structured schedule fields rather than relying on an opaque JSON blob. The exact supported schedule columns must match the approved schedule vocabulary. D-191 approves the structured fields above: `DAILY` means every local calendar day; `SELECTED_WEEKDAYS` uses a non-empty weekday bitmask to define scheduled days; `FLEXIBLE_WEEKLY_TARGET` has no mandatory weekdays and may store optional preferred weekdays only as routine guidance. `target_period` identifies whether `target_value` is a daily or weekly goal; quantity/duration progress sums compatible recorded units over that period, while completion-only/effort-aware weekly goals count qualifying completed dates, not arbitrary invented numeric values. The saved app-level week-start preference defines every weekly boundary. For `DAILY` and `SELECTED_WEEKDAYS` schedules, `target_period` must be `DAY`; a `FLEXIBLE_WEEKLY_TARGET` uses `WEEK`. Weekday masks use a locale-independent 7-bit integer encoding approved by D-195: Monday=1, Tuesday=2, Wednesday=4, Thursday=8, Friday=16, Saturday=32, Sunday=64. Combine selected days with bitwise OR (equivalently, add the distinct bit values); valid non-empty masks are 1–127. `scheduled_weekdays_mask` is required and non-empty only for `SELECTED_WEEKDAYS`; `DAILY` and `FLEXIBLE_WEEKLY_TARGET` do not require a scheduled-day mask. `preferred_weekdays_mask` is optional for `FLEXIBLE_WEEKLY_TARGET`, guidance only, and if present must use only the same seven defined bits. Reject unknown bits and invalid schedule/mask combinations in the domain layer. Enforce the full allowed schedule/target/mask combinations: `DAILY` requires `target_period=DAY`, `scheduled_weekdays_mask=NULL`, and `preferred_weekdays_mask=NULL`; `SELECTED_WEEKDAYS` requires `target_period=DAY`, `scheduled_weekdays_mask` in 1–127, and `preferred_weekdays_mask=NULL`; `FLEXIBLE_WEEKLY_TARGET` requires `target_period=WEEK`, `scheduled_weekdays_mask=NULL`, and `preferred_weekdays_mask` either NULL or in 1–127. Every present mask must contain only the seven defined bits; reject rather than silently trim unknown bits. Mirror these invariants in the domain layer and proposed database checks so invalid combinations cannot be saved by any write path. The saved app-level week-start preference affects weekly boundaries, not the fixed weekday-bit mapping; locale affects only the initial week-start default.
3. **`habit_entries`** — individually correctable quantity/duration sessions: `entry_id` (UUID primary key), `habit_id` (foreign key), `local_date`, `value_units` (non-negative integer; zero is valid), nullable `entry_note`, `created_at_utc_ms`, `updated_at_utc_ms`, and nullable `idempotency_key`. Do **not** add a unique constraint on (`habit_id`, `local_date`). A partial unique index on non-null `idempotency_key` prevents replay of the same logical submission; the caller must reuse the same key only for retries of that submission, never for a distinct intentional entry. Keep units canonical per habit version and do not mix incompatible units in a daily sum.
4. **`habit_day_outcomes`** — explicit non-numeric positive/effort states only: `outcome_id` (UUID primary key), `habit_id`, `local_date`, `outcome_kind` (completion-only complete or effort-aware selection), nullable `effort_level`, nullable `idempotency_key`, and created/updated instants. Unique constraint: (`habit_id`, `local_date`) so there is at most one current day-level positive/effort outcome for a habit/date. The domain layer validates outcome kind against the effective tracking mode and prevents contradictory numeric-entry/day-outcome states. Completion-only and effort-aware outcomes cannot substitute for quantity/duration entries, and quantity/duration entries cannot satisfy a non-numeric tracking mode. Do not store a user-entered `miss` outcome: missed status is derived from the applicable schedule and absence of qualifying activity after the scheduled day has passed. A numeric zero is a `habit_entries` row, not an outcome. No record before day-end is unrecorded; after a scheduled day passes with no qualifying activity, derive missed. Genuine activity may be explicitly backdated to its actual local date and must recalculate that date's result and dependent summaries. A journal memo alone never changes habit status.
5. **`habit_date_notes`** — optional date-level context independent of session notes: `note_id` (UUID), `habit_id`, `local_date`, `body`, created/updated instants. Unique constraint: (`habit_id`, `local_date`); deleting the note does not delete tracking entries.
6. **`journal_entries`** — saved independent reflections: `journal_entry_id` (UUID), `local_date`, `body`, nullable `title`, nullable primary/secondary mood codes, nullable `prompt_id`, nullable `linked_habit_id` foreign key to `habits` with `ON DELETE SET NULL`, `created_at_utc_ms`, and `updated_at_utc_ms`. Multiple entries per date are allowed; no date-level uniqueness. Deleting a habit clears only the optional link and preserves the journal entry and its content. Editing preserves ID and creation instant. A date correction affects only this journal entry.
7. **`journal_drafts`** — unsaved content kept separate from saved entries: `draft_id` (UUID), optional `local_date`, body/title/mood/prompt fields as needed, created/updated instants, and optional `source_context`. A draft is not a journal entry until explicit Save. Multiple drafts may exist; do not silently overwrite one draft with another.
8. **`app_settings`** — typed, versioned local preferences such as week-start, reminder opt-in, quiet hours, theme, and backup preferences. Use a stable setting key and validated value representation; do not store personal journal content here.
9. **`reminder_deliveries`** — durable deduplication ledger: `delivery_key` (unique primary key for a logical occurrence), reminder type, optional habit ID, intended local date/week key, status, scheduled/attempted/delivered instants, opaque platform-notification tag/ID where needed, and dismiss/suppression metadata as required. Persist the key before or atomically with scheduling state so restart/reschedule does not create duplicate logical deliveries. Do not store message copies containing personal text.


10. **`restore_sessions`** — restore-operation state needed to recover safely from interrupted Replace/Merge: stable session ID, mode, format version, state, start/update instants, validated manifest/counts, and safety-backup reference/status. Proposed state values are `IN_PROGRESS`, `RECOVERY_REQUIRED`, `COMPLETED`, `COMPLETED_WITH_CONFLICTS`, and `FAILED_SAFE`. Do not store raw secrets or passwords. A session with unresolved child conflicts uses `COMPLETED_WITH_CONFLICTS` and remains durable/discoverable; after its last conflict is successfully resolved, change it to `COMPLETED`. This state is distinct from an interrupted/incomplete live transaction. Only a minimal context envelope for conflict-bearing completed sessions is portable; never export a local safety-backup reference or active transaction state.
11. **`restore_conflicts`** — unresolved record conflicts: stable conflict ID, required `restore_session_id` foreign key to the parent `restore_sessions` row, canonical record type/key (entity ID or the collided unique key), both validated version payloads, and creation instant. A row exists only while the conflict is unresolved; do not store a separate status column. Use a unique constraint on (`restore_session_id`, `record_type`, `record_key`) so one restore session cannot create duplicate conflict rows for the same logical collision. Resolution applies the selected safe outcome and deletes the conflict row in the same successful transaction. The parent session remains durable until no unresolved children exist. Journal text inside a conflict remains private local data, must not enter logs/notifications, and is included in portable backup while unresolved so it cannot be lost on migration. When conflict bundles are restored, create a fresh local parent session and remap the conflict parent references instead of importing a foreign session ID as a live foreign key.
12. **`notification_cancel_outbox`** — temporary, idempotent cleanup work for OS notifications after habit deletion: opaque notification tag/ID, creation/attempt timestamps, and minimal status/error category. No habit name, journal text, or stable habit ID is needed. Remove a row after confirmed cancellation; retry pending rows at startup. Exclude this platform-specific outbox from portable backup.

### Relationships, indexes, and invariants

- Foreign keys must be enabled on each SQLite connection. Owned habit tables reference `habits`; permanent deletion removes owned history/configuration/delivery rows in a controlled transaction. A nullable journal linked-habit reference uses `ON DELETE SET NULL`, never cascading to delete the journal entry. Global settings and independent drafts are unaffected by habit deletion. OS notification cancellation is handled outside the SQLite transaction through an opaque cancellation outbox so external platform work is retried safely.
- Minimum indexes: `habit_versions(habit_id, effective_from_local_date)` unique; `habit_entries(habit_id, local_date, created_at_utc_ms)`; partial unique idempotency-key indexes on `habit_entries` and `habit_day_outcomes` when non-null; `habit_day_outcomes(habit_id, local_date)` unique; `habit_date_notes(habit_id, local_date)` unique; `journal_entries(local_date, created_at_utc_ms)`; `journal_drafts(updated_at_utc_ms)`; `reminder_deliveries(delivery_key)` primary/unique plus pending-delivery index; `restore_conflicts(restore_session_id, created_at_utc_ms) plus its unique (restore_session_id, record_type, record_key) constraint; index restore_sessions(state, updated_at_utc_ms) for recovery/review queries`; and pending indexes for `notification_cancel_outbox`. The `restore_conflicts.restore_session_id` foreign key must prevent deleting a parent session while unresolved conflict rows still depend on it. Rows exist only while unresolved; resolve/delete each child atomically with applying its selected outcome, then mark the parent `COMPLETED` only when no unresolved child rows remain.
- Use integer UTC epoch milliseconds for instants and ISO `YYYY-MM-DD` strings for user-intended local date keys. Never derive an existing record's date key by converting its timestamp after a timezone change.
- Recompute daily/weekly totals and progress from source entries and the applicable `habit_versions`; derive missed status from schedule plus absence of qualifying activity after the scheduled day has passed. Do not make cached totals/status authoritative. Any cache introduced later must be rebuildable and invalidated transactionally. Journal entries/notes never count as activity evidence or alter habit status; a genuine backdated activity record does.
- All multi-row actions (save/edit/delete entry, change effective-dated configuration, archive/restore, permanent deletion, restore/merge, and reminder state updates) require explicit transaction boundaries. Validate input and mode/config compatibility before commit; show success only after commit.
- Stable UUIDs are generated once for each entity and retained for its lifetime; editing preserves identity. For a logical activity submission, generate an idempotency key and reuse that same key on retries; a distinct intentional entry gets a new key. Enforce uniqueness for non-null keys, while allowing null for records that do not need retry protection. Never deduplicate based only on equal values or close timestamps. This rule is owner-approved by D-190; it does not approve the complete proposed schema.
- Every habit configuration change must resolve an effective local date using the approved Apply today/Apply tomorrow interaction. The active configuration for a past date is the latest version whose effective date is not after that date. Schedule edits must not synthesize historical records. Under D-194, the first Apply-today change creates today's configuration version. A further same-day edit replaces that version only if no qualifying habit activity has been recorded today. Once qualifying activity exists, preserve today's configuration and activity history and offer Apply tomorrow; Cancel makes no change. Apply tomorrow creates or updates tomorrow's not-yet-effective version. This resolves the repeated Apply-today policy but does not approve the complete schema.
- Portable backup format must be versioned and map every owned entity/relationship explicitly. Restore validates all records, IDs, schema compatibility, and constraints before mutation; merge/replace behaviour remains governed by approved backup decisions.

### Partial schema decisions approved; complete proposal and remaining gates

**Owner decisions recorded — approved:** (a) use effective-dated `habit_versions` snapshots as the source of historical schedule, target, tracking-mode, and other habit-configuration meaning; past versions remain unchanged and configuration changes apply prospectively from their effective local date (previously approved schema decision); and (b) store numeric/duration activity separately from non-numeric daily outcomes (D-189). `habit_entries` retains each quantity/duration session, permits multiple entries per habit/date, and treats explicit zero as a real entry. `habit_day_outcomes` stores at most one current completion-only or effort-aware outcome per habit/date. The domain layer must reject a day outcome that conflicts with the effective tracking mode, reject incompatible numeric entries/outcomes for that mode, and derive missed status rather than storing a miss. These are partial schema decisions only and do not approve the complete schema for implementation. **Owner decisions recorded:** (c) D-192 confirms both optional per-entry notes and one optional habit/date context note; they serve different purposes and remain distinct from general journal entries. The proposed `habit_date_notes` table permits at most one note per habit/local date, while each numeric/duration entry may independently carry its own optional note. The daily note may provide the easiest/default note path; neither note changes activity totals or habit outcome. (d) D-191 approves structured schedule fields and D-195 approves the fixed Monday-first 7-bit weekday-mask encoding; confirm constraints, persistence and behavior in authorised technical review. Stable UUID identity and nullable idempotency keys with uniqueness when present are now approved as D-190. D-188 resolves the missed-day rule: no manual miss outcome; derive missed status after a scheduled day passes without qualifying activity, permit genuine explicitly backdated activity to recalculate that date, and never let a journal memo change habit status. D-193 resolves the related skipped-state question: v1 has no explicit habit-day Skip action or persisted skipped outcome; optional skipping of journal prompts/reflections remains unaffected. These are partial approvals only. Do not implement or migrate until the complete proposal is approved and the current version-1 schema has been inspected under an explicitly authorised technical-validation gate.

**Delegated planning default for permanent habit deletion:** the database transaction records opaque notification-cancellation identifiers in `notification_cancel_outbox`, removes habit-owned tracking/configuration/delivery rows, nulls the optional linked-habit ID on independent journal entries, and deletes the habit identity. After commit, cancel OS notifications and remove outbox rows only after successful cancellation; failed or interrupted cancellation is retried on startup. Every delivery worker re-checks that the habit still exists and is active immediately before posting. The outbox holds no habit name or journal text and is excluded from portable backup. This is a planning default only, not implemented or verified, and may be overridden before schema approval. D-194 resolves repeated Apply-today behavior and D-195 resolves the weekday-mask encoding as documented above. D-193 resolves explicit habit-day skipping: do not expose a Skip action or store a skipped outcome in v1. Do not infer remaining product behavior from D-187–D-196; D-196 defines the delegation process, not new product requirements.

## Undo and recovery — delegated planning proposal

**Status: proposed for owner review, not implemented.** To satisfy the product requirement for recent recovery without creating an unbounded undo history:

- After a successfully committed single-record tracking mutation (create/log/complete/edit of one numeric entry, day outcome or habit-date note), expose one 8-second snackbar Undo. The undo token identifies the exact entity and mutation; creating a new mutation replaces the prior pending token.
- Undo runs as a guarded transaction. A create/log undo removes only the exact record/outcome created by that mutation. An edit undo restores the captured prior fields only if the entity still has the expected post-edit version. If another change makes the inverse unsafe, do not overwrite newer data; explain that the item can be corrected from History instead.
- Do not deduplicate by value or timestamp. Undo references the original stable UUID and does not create a second activity entry. It recalculates dependent totals/insights from source records.
- This is short-lived in-session recovery, not a durable undo log. If the window expires or the process dies, the saved state remains as committed and the Undo affordance disappears. Users can still edit/delete supported records through normal History flows.
- Confirmed journal-entry deletion, permanent habit deletion, delete-all and Replace/Merge restore are not snackbar-undoable. Their existing confirmation and restore safety-backup protections remain authoritative. The UI must state that confirmed permanent deletion may not be recoverable in Dayseed; copies in user-managed backups/exports are separate.
- Never show Undo before the original mutation commits. If the save fails or the result is uncertain, preserve the record/draft and offer a retry/recovery message, not a false success.

Owner must accept this proposal or explicitly defer the relevant UX before Gate A. Acceptance tests are planned only; no runtime behaviour is implied.

## Date and time policy
Separate timestamps (instants) from local calendar dates. Habit completion belongs to the local calendar date explicitly selected/confirmed for the record, never to a UTC date merely because the timestamp converts to that date. Use one injectable clock/date-policy service for all date-sensitive rules.

### Approved date/time and history contract (D-187 planning baseline)

- **Canonical day key:** store a local calendar date (YYYY-MM-DD) separately from event timestamps. A record's day key is the date the user intentionally chose when recording; store creation/update instants separately for ordering and recovery.
- **Default date for a new entry:** the current device-local date when the user starts/commits the action. If the user explicitly selects a past/future date in a supported flow, use that selected date and make it visible before save. Do not silently move records when the device time zone changes.
- **Travel/time-zone changes:** use the current device-local calendar for new default dates, Today, week labels, and future local reminder scheduling. Preserve existing date keys and event instants; do not reinterpret historical records just because the current zone changed.
- **Week boundaries:** derive week start/end from the user's saved week-start preference; use the device/locale convention as the initial default where available. Apply the same helper to weekly targets, reminders, insights, and calendar UI.
- **Backdating:** allow explicit historical corrections and retrospective journal entries where the product flow supports them. Require explicit save; update only the selected record/entry and dependent summaries. A journal date change must never move habit records.
- **Clock changes / uncertain time:** do not fabricate elapsed time or shift stored records. If timestamps appear inconsistent, preserve user data, avoid duplicate comeback/reminder events, and use conservative eligibility until time confidence is re-established. Do not claim a precise absence duration without sufficient evidence.
- **Daylight-saving changes:** use platform time-zone rules for local date boundaries; store instants independently and test skipped/repeated local clock times where the relevant time zone observes DST. Do not use fixed 24-hour arithmetic for calendar-day logic.
- **Scheduled reminders:** compute eligibility from local calendar/week policy and persist a stable delivery key for each logical reminder occurrence. Respect explicit reminder opt-in, OS permission, quiet hours and approved caps. On zone changes/restarts, recalculate future delivery without duplicating an already-delivered occurrence. Android may defer delivery.
- **Comeback timing:** preserve the specific approved rules in D-146–D-160 (including full local-calendar-day thresholds and no duplicate display after zone changes). This shared policy does not override their trigger-specific rules.
- **Historical schedule/target interpretation:** preserve the settings effective for each historical date. Schedule/target edits apply prospectively using the approved effective-date choice; they do not silently rewrite past records or create missed records retroactively.
- **Habit lifecycle:** archive is the default non-destructive way to remove a habit from active use; archived history remains accessible. Permanent deletion is a separate, clearly explained user action and must not delete independent journal entries.
- **Manual clock changes:** do not use wall-clock jumps alone to infer activity, absence, or elapsed reminder intervals. Preserve saved dates and values, deduplicate logical events, and use conservative eligibility when time confidence is uncertain.

This is the approved v1 planning baseline under D-187; trigger-specific approved decisions remain authoritative where more specific. It does not prove implementation correctness. Exact storage columns/indexes, transaction boundaries, migration safety, and test fixtures remain to be finalised and technically verified after the planning gate.

## Offline-first rules
- No network request is required for core actions.
- A successful save means data is committed locally.
- Network absence must not prevent navigation, writing, editing, or history viewing.
- Initial v1 has no account, online backup, or cross-device sync service. Premium online backup/sync is a future capability only and requires a separate explicit product, privacy/security, consent, data-flow, retention/deletion, conflict-resolution, and migration gate.
- **Android platform backup (D-186):** exclude sensitive Dayseed app data from Android Auto Backup/device-transfer by default. Implement and verify explicit backup/data-extraction rules for private records and drafts. This is distinct from Dayseed's user-controlled portable backup and opt-in file-based Auto Backup to a selected destination. Do not claim the exclusion is effective until configuration and supported OS/device-transfer paths have been inspected and tested.
- Ads, if approved, load asynchronously and never delay core UI.

## Failure handling
- Handle database open/write failures with clear recovery messages.
- Use transactions for operations affecting multiple records or settings.
- Avoid silent data loss and never log journal contents.
- A migration failure must preserve recoverable data and must not pretend migration succeeded.
- Notifications may be delayed or restricted by Android; in-app behaviour must remain correct without them.
